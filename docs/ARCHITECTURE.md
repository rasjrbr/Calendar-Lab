Calendar Lab – Architecture Overview

This document describes the architecture of the Calendar Lab system, its components, data flow, and core design principles.

––––––––––––––––––––
	1.	Purpose
––––––––––––––––––––

Calendar Lab ingests a public calendar (ICS / WebCal) generated by iFlightNeo through third-party calendar platforms (iCloud, Google Calendar, Samsung Calendar, Outlook), normalizes and cleans the data, applies aviation-specific operational logic, and republishes a stable, clean ICS calendar for final user consumption.

The system exists because the iFlightNeo source calendar is unreliable, destructive, and unsuitable for long-term operational or regulatory use.

––––––––––––––––––––
2. High-level data flow
––––––––––––––––––––
	1.	Source calendar
iFlightNeo exports flight, activity, and report data into a user-selected calendar.

That calendar is then exposed publicly via:
	•	webcal://
	•	https:// ICS endpoint

Important characteristics of the iFlightNeo source:
	•	Past data is deleted and recreated.
	•	Events may be duplicated.
	•	Event structure and titles change without notice.
	•	Timezone information is often missing or inconsistent.

The source calendar must always be treated as volatile and untrusted.
	2.	Worker (Python, Docker)

The worker is the brain of the system.

Responsibilities:
	•	Periodically download the source ICS.
	•	Parse all VEVENT entries.
	•	Normalize all times (assume SOURCE_TZ, convert to UTC).
	•	Deduplicate events using (user_id, source_uid).
	•	Persist normalized events into PostgreSQL.
	•	Apply a deterministic transformation pipeline.
	•	Generate a clean, final ICS per user.

Transformation pipeline (current and planned):
	•	Remove disposable events (e.g. “Start Time:”).
	•	Clean titles by removing prefixes:
Activity :
Flight :
Report Time :
	•	Normalize Activity and Day Off events.
	•	Resolve overlaps between Activity and Report Time events.
	•	Prevent ground activities from polluting duty calculations.
	•	Future step: duty limits, leg counting, overnight limits, fatigue logic.

The worker is idempotent:
	•	It can run repeatedly without corrupting data.
	•	Output calendars can always be regenerated from the database.

	3.	PostgreSQL

PostgreSQL is the authoritative data store.

Responsibilities:
	•	Store normalized raw events.
	•	Enforce deduplication across sync cycles.
	•	Preserve historical data even when source deletes it.
	•	Support statistics and analytics (monthly totals, duty metrics).
	•	Enable future reporting and optimization logic.

The database is the single source of truth.
	4.	NGINX

NGINX serves the final output calendars.

Responsibilities:
	•	Expose generated ICS files over HTTP.
	•	Serve static files only.
	•	No business logic.
	•	No parsing.

Users subscribe to these ICS files using:
	•	webcal://
	•	https://

The client never consumes iFlightNeo directly.
	5.	Client calendars

Supported clients include:
	•	Apple Calendar
	•	Google Calendar
	•	Android calendars
	•	Outlook

Clients subscribe only to the cleaned output calendar.

––––––––––––––––––––
3. Containers
––––––––––––––––––––

calendar_worker
	•	Python-based service.
	•	Handles ingestion, parsing, normalization, optimization, and publishing.
	•	Stateless by design; relies on PostgreSQL and shared volumes.

calendar_postgres
	•	PostgreSQL 16.
	•	Stores raw and processed event data.
	•	Persists data across container restarts.

calendar_nginx
	•	Static file server.
	•	Exposes /var/www/calendars/{user}.ics.
	•	No application logic.

––––––––––––––––––––
4. Timezone strategy (critical)
––––––––––––––––––––

Timezone handling is non-negotiable.

Rules:
	•	All regulatory and fatigue logic is computed in local BRT.
	•	All stored timestamps are UTC.
	•	All output ICS files use UTC (Z).
	•	Source ICS frequently uses floating local times with no timezone.

Worker assumptions:
	•	SOURCE_TZ = America/Sao_Paulo
	•	All floating times are interpreted as SOURCE_TZ.
	•	All times are converted to UTC immediately after parsing.

This strategy ensures:
	•	Deterministic calculations.
	•	Correct duty and overnight evaluation.
	•	Compatibility across calendar clients.

––––––––––––––––––––
5. Data philosophy
––––––––––––––––––––

Core principles:
	•	Raw source data is unreliable.
	•	The database is the source of truth.
	•	Output calendars are disposable.
	•	Output can be regenerated at any time.
	•	Past data older than approximately two months is intentionally ignored for reprocessing.

The system is designed to recover cleanly from:
	•	Source calendar corruption.
	•	Parsing logic changes.
	•	Regulatory rule updates.

––––––––––––––––––––
6. Architectural boundaries
––––––––––––––––––––
	•	iFlightNeo is a data source only.
	•	The worker owns all business logic.
	•	PostgreSQL owns persistence and integrity.
	•	NGINX owns exposure, not logic.
	•	Client calendars are passive consumers.

Any violation of these boundaries is considered a design error.
